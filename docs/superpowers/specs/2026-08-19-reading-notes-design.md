# 読書メモ機能 設計メモ

- 種別: 設計検討（未決定事項を含む）
- 対象: AI チャットとは別に、本ごとの Markdown 読書メモを取れるようにする機能
- 最終更新: 2026-08-19

本を読みながら自分の言葉でメモを取り、PDF の選択箇所を引用として差し込み、Markdown で書き出し、最終的には AI に推敲させる。優先度は次の順で、上から順に単独で価値が出るように切る。

1. 読書メモが取れること
2. PDF の選択箇所（ページ / 引用文）を挿入しながらメモを取れること
3. Markdown でダウンロードできること
4. AI がメモに関わること（推敲・質問）

この文書は実装前の検討結果であり、末尾の「決定待ち」がまだ空いている。実装に入る前にそこを埋めること。

## 既にあるもの

新しく発明が要る箇所を見誤らないために、流用できるものを先に並べる。

| 要るもの                             | 現状                                                                                                                                 |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| Markdown レンダリング                | `react-markdown` + `remark-gfm` + `rehype-highlight` + `mermaid` が依存にあり `ChatMessageBubble` で稼働中。プレビューはほぼ実装ゼロ |
| 引用文からページを解決する経路       | `chatService.findPageNumber` / `GET /pdf/:pdfId/locate` / `#:~:text=` の一式が完成済み                                               |
| デバウンス保存と離脱時 flush         | `useReadingStateSync` がそのまま手本。`save` と `debounceMs` を DI 済みで偽タイマーでテストできる                                    |
| 入力中にショートカットが暴発しない   | `useKeyboardShortcuts` の `isEditableTarget` が `TEXTAREA` を既に除外している。追加対応は不要                                        |
| 失敗の運び方・zod スキーマ・SWR の型 | `resultFetcher` / `src/shared/schemas/` / `ApiError` のレールが敷かれている                                                          |

Phase 1 で新規に設計が要るのは**保存の信頼性だけ**である。

## 採用する方式

### 1 冊 1 枚の Markdown 文書とする

メモは本ごとに 1 枚。複数枚は持たない。

このアプリには既に「断片的な注釈」の軸がある（`selections` と、それにぶら下がる `chat_messages`）。ここへ「複数のメモ」を足すと、ハイライトとメモの使い分けが読者にとっても実装にとっても曖昧になる。役割を次のように分ける。

- **ハイライト** — 本の中の場所に付ける印。断片。AI との会話がぶら下がる
- **メモ** — 読者自身の統合文書。1 冊に 1 枚。ハイライトを引用しながら育てる

この形なら一覧 UI も作成・削除・並び替えも要らず、「Markdown でダウンロード」が「この本のメモ .md」で自明に決まり、AI の推敲対象も一意になる。複数枚は後から足せるが、複数枚から 1 枚へ畳むことはできない。

### 置き場所は右ペインのタブ

リーダーの現在の構造は、広い画面が `[PdfViewer | ハンドル | ChatArea]`、狭い画面が PDF 全幅 + `ChatSheet` である。メモは**右ペインにタブを設けて、チャットと切り替える**。

| 案                                  | 判断                                                                                                                                                |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 右ペインをタブ化（チャット / メモ） | **採用。** 幅の追加がゼロ。`HANDLE_WIDTH` と `leftWidth` の算術、`ChatSheet`、`chatPanelOpen` の復元にそのまま乗る                                  |
| 3 ペイン                            | 却下。1280px ではチャットを畳んでやっと見開きになる程度の余裕しかなく、PDF が潰れる                                                                 |
| 全画面オーバーレイ / 別ルート       | Phase 1 では却下。Phase 2 の「PDF から挿入」が PDF とエディタの同時表示を要求する。ただし将来「集中して書くモード」としてタブと併用するなら筋は良い |
| PDF の下に引き出す                  | 却下。PDF の高さを奪う。CLAUDE.md の「ページ全体が必ず見える」約束と正面から衝突する                                                                |

タブ化に伴い `chatPanelOpen` の意味は「チャットが開いているか」から「右ペインが開いているか」へ広がる。列名 `last_read_chat_panel_open` はそのままにし、意味だけ広げる。リネームはマイグレーションを伴い、得るものが名前だけなので見合わない。

「どちらのタブを見ていたか」を本ごとに保存するかは Phase 1 では決めない。既定をチャットにして始める。

### メモは `pdfs` の列ではなく `notes` テーブルに置く

```
notes: id / pdf_id (unique, FK cascade) / body / version / created_at / updated_at
```

`pdfs` に列を足さない理由は 2 つある。

- `readPdf` / `storePdf` は drizzle が `pdfs` の全列を明示列挙するため、本を開くたびに本文（実書籍で 213KB）に加えてメモまで D1 から読むことになる。CLAUDE.md の「応答に使わない列を select しない」に反する
- 別テーブルなら `GET /api/pdf/:pdfId` を一切触らずに済み、本を開く経路への退行リスクがゼロになる

エンドポイントは `GET /api/pdf/:pdfId/note` と `PUT /api/pdf/:pdfId/note` の 2 本。`requireSession` の内側に自動的に入る（middleware が全ルートより先に登録されているため、新しいルートは黙って守られる）。

### 保存の信頼性は読書位置と別の規約にする

これが Phase 1 の本題である。

CLAUDE.md は読書位置について「**保存に失敗しても再送はしない**」「**後に書いた方が勝つ（利用者が 1 人なので調停はしない）**」と定めているが、**この規約をメモに持ち込むと文章が消える**。ページ番号を失うことと段落を失うことは別の事故であり、同じ扱いにはできない。差分は 3 点。

**保存状態を常時見せる。** 読書位置は失敗したときだけ帯を出すが、メモは「保存済み / 未保存 / 保存失敗」を常に出す。書いたものがサーバにあると確認できないエディタは信用されない。

**`keepalive` の 64KB 上限を踏む可能性がある。** 離脱時 flush は読書位置（数十バイト）なら安全だが、育ったメモは超えうる。`localStorage` にドラフトを鏡写しし、次に開いたときサーバ版より新しければ復帰を提案するのが素直な保険になる。

**競合を検出する。** 端末をまたいで同じ本を開くのはこのアプリの前提そのもの（読書位置同期の存在理由がそれ）なので、メモでも普通に起きる。`version` を持って `WHERE version = ?` で弾き、409 なら上書きせず読者に見せる。列 1 本と `WHERE` 句 1 つで済むうちに入れておくのが安く、メモが溜まってからの後付けは難しい。

### エディタは textarea とライブプレビュー

素の `<textarea>` にプレビューを添える形にする。CodeMirror や ProseMirror は重いうえ、リッチな WYSIWYG は Phase 4 の「AI が Markdown を書き換える」と食い合う。ソースが正であることを保つのが結局いちばん強い。

「エディタらしさ」は太字・見出し・リストのツールバーで足りる。これは次の形の DOM 非依存な純粋関数に落ちるので、このリポジトリの流儀（`keybindings.ts` / `sseParser.ts` / `isSubmitKey.ts`）にそのまま嵌まる。

```ts
applyMarkdownCommand(text, selStart, selEnd, command): { text, selStart, selEnd }
```

IME は textarea なら壊れないが、エディタ内に送信系のショートカットを足すなら `isSubmitKey` と同じく `isComposing` を見ること。

## Phase 2 — PDF の選択箇所を挿入する

### 「行」は諦め、ページと引用文をアンカーにする

PDF に行番号という概念は無い。テキストレイヤーの span を y 座標で束ねれば擬似的な行は作れるが、フォントや段組みで簡単に崩れるうえ、「p.42 の 17 行目」は読者にとって意味を持たない。

**アンカーはページ番号と引用文**にする。これは `/locate` と `#:~:text=` が既に使っている単位そのもので、既存の機構にそのまま乗る。

### 挿入はハイライトを作る

挿入操作は `selections` の行を 1 つ作る。`useAskAboutSelection` の保存経路をほぼそのまま再利用でき、メモからその箇所へ戻る導線が既存の `?selection=` 復元だけで成立する。作らない場合、メモ専用のアンカー機構をもう一系統持つことになる。

挿入される文字列の案:

```markdown
> 選択したテキスト

<sup>[p.42](?page=42&selection=01KZ...)</sup>
```

プレビュー内のこのリンクはページ遷移させず本の中を移動させたいので、`a` レンダラを差し替えて内部リンクを横取りする。`ChatMessageBubble` が `CitationLink` でやっているのと同じ形。

### 挿入まわりの細部

- 挿入先は textarea のキャレット位置。フォーカスが無ければ末尾
- 右ペインがチャットタブならメモタブへ切り替える。狭い画面ならシートを上げる。`useAskAboutSelection` の「質問することはチャットを開くことでもある」と同じ意味論
- `SelectionPopover` と `SelectionActionBar` に「メモに挿入」を足す。狭い画面のバーは「AIに質問」と 2 択になる

## Phase 3 — Markdown でダウンロード

クライアント側だけで完結する（Blob と `<a download>`）。決めるのは 2 点。

- **ファイル名** — 本の `fileName` から拡張子を落として `.md`
- **相対リンクの扱い** — Phase 2 で埋めた `?page=42&selection=...` は書き出した .md の中では壊れたリンクになる。公開 URL で絶対化するか、`(p.42)` のただのテキストに落とすか。**後者を推奨**する。絶対 URL はログインの内側にあるので、他人に渡しても開けない

メモに取り込んでいないハイライトを付録として末尾に足すかは好みで決める。

## Phase 4 — AI

性質の違う 2 つが混ざっているので分ける。

### 4-a. 推敲（変換）

入力がメモ本文、出力が直された Markdown。会話ではなく変換なので**履歴が不要で、スキーマ変更がゼロ**。ここから始めるのが安い。

外してはいけない点が 3 つ。

- **黙って上書きしない。** 提案として出し、「適用 / 破棄」を明示的に押させる。適用後の undo 用に直前の本文を保持する
- **対象はメモ全体ではなく選択範囲**を推奨する。速く、安く、読者が結果を検証できる
- **`fullText` をコンテキストに載せない。** 既存チャットが最初のトークンまで 10 秒前後かかるのは 200 ページの全文を積んでいるためで、推敲まで同じコストを払う理由は無い。メモ本文と、メモ内の引用だけで足りる

### 4-b. メモについての質問（会話）

こちらはスキーマにぶつかる。`chat_messages.selection_id` は NOT NULL かつ `selections` への FK なので、ハイライトに紐づかない会話を置けない。選択肢は 3 つ。

1. `selection_id` を nullable にし `note_id` を足す（既存クエリ全体に波及する）
2. 会話テーブルを別に立てる
3. 履歴を持たない一問一答にする（スキーマ変更ゼロ）

Phase 4 の最初としては 3 で足りる。そもそも「本全体についての会話」がこのアプリに無い（会話は必ずハイライト単位）ので、これは**メモ機能が炙り出した別の欠落**として切り出して考える。

### 4-c. ハイライトからメモの下書きを生成する

費用対効果はおそらくこれが最も高い。既存データだけを使い、一問一答で済み、スキーマ変更が無く、そして「白紙のエディタ」というメモ機能最大の障壁を壊す。4-a より先に置く判断もありうる。

## テスト方針

- **純粋関数を先に切る。** Markdown コマンドの適用、挿入文字列の組み立て、エクスポート本文とファイル名は DOM に依存しない関数にして jsdom で単体テストする
- **自動保存は `useReadingStateSync` と同じ形。** `save` と `debounceMs` を DI し、偽タイマーで進める。競合（409）と復帰提案の分岐もここで見る
- **新エンドポイントは D1 に触るので `test/worker/**`\*\* に置く
- **E2E は fixture 共有の罠を踏む。** 3 つの spec は同じファイルの本を使うので同じ `pdfId` を共有する。各 spec の `openTestBook` がハイライトと読書位置をリセットしているのと同じく、**メモもリセットが要る**。忘れると先行テストの残骸で後続が落ちる
- マイグレーションを足すので `pnpm run db:migrate:local`。バインディングは増えないので `vp exec wrangler types` は不要
- 完了時に **CLAUDE.md を更新する**。特に「メモの保存規約が読書位置と違う理由」は、あのドキュメントの粒度なら必ず書き残す対象になる

## 決定待ち

実装前にここを埋める。括弧内はこの文書の推奨。

1. メモは 1 冊 1 枚か、複数枚か（1 枚）
2. 置き場所は右ペインのタブか、別の場所か（タブ）
3. 競合検出（`version` 列）を Phase 1 に入れるか、last-writer-wins と localStorage の保険で妥協するか（Phase 1 に入れる）
4. 挿入がハイライトを作ることに違和感が無いか（作る）
5. AI の入口は 4-a 推敲か、4-c ハイライトからの下書き生成か（未定）

## スコープ外

- 複数メモ、メモの一覧・検索・タグ
- 本をまたいだメモの横断（ノートブック的な使い方）
- リッチテキスト編集、WYSIWYG
- 画像の添付
- メモの共有・公開
- 本全体を対象とした会話（4-b の 1 と 2 の案。別課題として切り出す）

## 付録: クラウド環境からのデプロイ（保留）

同じ検討の場で出た別件。結論だけ残す。

Claude Code のクラウド実行環境からは、現状 Cloudflare へデプロイできない。`CLOUDFLARE_API_TOKEN` が環境変数に無く、`~/.wrangler` の資格情報も無く、`wrangler login` はブラウザを開く対話フローなのでコンテナからは完了できない。

通すなら、Workers 用のスコープ付き API トークン（Workers Scripts:Edit / D1:Edit / Workers R2 Storage:Edit をアカウント限定）を作り、環境の env vars に登録する。Global API Key は使わない。持ち込む必要があるのはこのトークンだけで、`.dev.vars` は `.dev.vars.example` のダミー値のコピーで足り、`wrangler secret put` で入れた本番の秘密は Worker 側に既にあるのでデプロイのたびに渡し直すものではない。

留意点は 3 つ。トークンの権限がミスの上限を決めること。セッションのトランスクリプトは残るのでツール出力に値を出さない運用が要ること。そして `wrangler d1 migrations apply --remote` は不可逆で、デプロイと違って戻せないこと。この最後の 1 つだけは自動で走らせず、都度確認する運用にする。
